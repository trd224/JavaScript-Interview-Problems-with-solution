Pages Router vs App Router

A complete side-by-side comparison of Next.js's two routing systems — folder structure, data fetching, rendering, layouts, navigation, metadata, API handling, caching and more.

◀ Pages Router (pages/) App Router (app/) ▶
PAGES ROUTER
APP ROUTER
1

Overview

The Pages Router is the original Next.js routing system built on the pages folder. The App Router, introduced in Next.js 13, is the modern system built on the app folder with React Server Components, nested layouts, streaming and the Metadata API.

Pages Router

  • Introduced in Next.js 1 (original router)
  • Every component in pages is a Client Component by default (fully hydrated)
  • Data fetching via getStaticProps / getServerSideProps / getStaticPaths
  • Shared UI via a single _app.js file
  • Considered legacy, still fully supported for existing apps

App Router

  • Introduced in Next.js 13, stable and recommended since Next.js 13.4
  • Every component in app is a Server Component by default
  • Data fetching directly inside components using async/await + fetch caching
  • Built-in nested layouts, loading states, error boundaries
  • Recommended for all new Next.js applications
2

Folder Structure & Routing

Both routers use file-based routing, but the file that defines a route and the way folders map to URLs is different.

Pages Router

Folder Structure
pages
├── index.js          → /
├── about.js           → /about
└── products
    └── [id].js         → /products/:id
pages/about.js
export default function About() {
  return <h1>About Page</h1>;
}

One file = one route. The file itself is the page.

App Router

Folder Structure
app
├── page.js             → /
├── about
│   └── page.js          → /about
└── products
    └── [id]
        └── page.js        → /products/:id
app/about/page.js
export default function About() {
  return <h1>About Page</h1>;
}

A folder = a route segment, and a special page.js file inside it makes that segment publicly accessible.

3

Dynamic Routes

Dynamic segments use the same square-bracket syntax in both routers, but params are read differently.

Pages Router

pages/products/[id].js
import { useRouter } from 'next/router';
export default function Product() {
  const router = useRouter();
  const { id } = router.query;
  return <h1>Product {id}</h1>;
}

Params are read at runtime on the client via router.query.

App Router

app/products/[id]/page.js
export default async function Product({ params }) {
  const { id } = await params;
  return <h1>Product {id}</h1>;
}

Params arrive as a Promise prop and are read on the server before render.

4

Data Fetching

The Pages Router needs special exported functions per rendering mode. The App Router fetches data directly inside async Server Components and controls the mode via the fetch cache option.

Pages Router — SSR

pages/products.js
export async function getServerSideProps() {
  const res = await fetch('https://api.example.com/products');
  const products = await res.json();
  return { props: { products } };
}
export default function Products({ products }) {
  return <div>{products.length}</div>;
}

Pages Router — SSG

pages/posts.js
export async function getStaticProps() {
  const res = await fetch('https://api.example.com/posts');
  const posts = await res.json();
  return { props: { posts } };
}

Pages Router — ISR

export async function getStaticProps() {
  return {
    props: { data: [] },
    revalidate: 60
  };
}

App Router — SSR equivalent

app/products/page.js
async function getProducts() {
  const res = await fetch('https://api.example.com/products', { cache: 'no-store' });
  return res.json();
}
export default async function Page() {
  const products = await getProducts();
  return <div>{products.length}</div>;
}

App Router — SSG equivalent

app/posts/page.js
async function getPosts() {
  const res = await fetch('https://api.example.com/posts');
  return res.json();
}
export default async function Page() {
  const posts = await getPosts();
  return <div>{posts.length}</div>;
}

App Router — ISR equivalent

export const revalidate = 60;
async function getData() {
  const res = await fetch('https://api.example.com/data');
  return res.json();
}
No getStaticProps, getServerSideProps or getStaticPaths exist in the App Router at all — everything is driven by fetch cache options and the revalidate export.

Static Params for Dynamic Routes

Pre-building dynamic pages at build time.

Pages Router

pages/products/[id].js
export async function getStaticPaths() {
  return {
    paths: [
      { params: { id: '1' } },
      { params: { id: '2' } }
    ],
    fallback: false
  };
}
export async function getStaticProps({ params }) {
  return { props: { id: params.id } };
}

App Router

app/products/[id]/page.js
export async function generateStaticParams() {
  return [
    { id: '1' },
    { id: '2' }
  ];
}
export default async function Page({ params }) {
  const { id } = await params;
  return <h1>Product {id}</h1>;
}
6

Rendering Model & Hydration

This is the single biggest architectural difference between the two routers.

Pages Router

Every component is a Client Component. The server renders HTML, then ships the full component JavaScript to the browser so React can hydrate the whole tree — even static, non-interactive parts.

Flow
Server renders HTML
        │
        ▼
Send HTML + full page JS bundle
        │
        ▼
Browser hydrates entire tree
Execution
Server  ✅
Browser ✅ (always, for every component)

App Router

Components are Server Components by default and render only on the server — no JS is shipped for them. Only components marked 'use client' are hydrated in the browser.

app/page.js — Server Component
export default async function Page() {
  const data = await fetch('https://dummyjson.com/products').then(r => r.json());
  return <ul>{data.products.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}
app/Counter.js — Client Component
'use client';
import { useState } from 'react';
export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
Result: App Router ships much less JavaScript to the browser by default, which is why it produces smaller bundles and faster hydration than the Pages Router.
7

Server vs Client Components (App Router only)

The Pages Router has no equivalent concept — every component behaves like a Client Component. The App Router splits capability between the two.

What Server Components CAN do

  • Directly await fetch(...)
  • Read cookies / headers on the server
  • Query a database directly
  • Keep API keys and secrets on the server

What they CANNOT do

  • useState / useEffect
  • onClick and other DOM event handlers
  • Browser-only APIs like window or localStorage

What Client Components CAN do

  • useState, useEffect, useRef
  • Event handlers (onClick, onChange, ...)
  • Browser APIs and animations
  • Third-party libraries that rely on the DOM

Marking a Client Component

'use client';
import { useState } from 'react';
export default function Login() {
  const [email, setEmail] = useState('');
  return <input value={email} onChange={e => setEmail(e.target.value)} />;
}
8

Shared Layouts

The Pages Router builds layouts manually. The App Router has a first-class, nested layout system.

Pages Router — _app.js

pages/_app.js
import Layout from '../components/Layout';
export default function App({ Component, pageProps }) {
  return (
    <Layout>
      <Component {...pageProps} />
    </Layout>
  );
}
components/Layout.js
export default function Layout({ children }) {
  return (
    <>
      <header>Header</header>
      <main>{children}</main>
      <footer>Footer</footer>
    </>
  );
}

One global layout only. Per-section layouts require manual composition inside each page.

App Router — layout.js

app/layout.js — Root Layout (required)
export default function RootLayout({ children }) {
  return (
    <html>
      <body>{children}</body>
    </html>
  );
}
app/dashboard/layout.js — Nested Layout
export default function DashboardLayout({ children }) {
  return (
    <section>
      <nav>Dashboard Nav</nav>
      {children}
    </section>
  );
}

Layouts can be nested per folder, persist across navigations without re-rendering, and don't lose state (e.g. video playback, form input).

Navigation & useRouter

The Link component exists in both, but useRouter is imported from a different module and exposes a different API.

Pages Router

Import
import { useRouter } from 'next/router';
Navigate + read query
const router = useRouter();
router.push('/about');
console.log(router.query.id);
Link
import Link from 'next/link';
<Link href="/about">About</Link>

App Router

Import
import { useRouter } from 'next/navigation';
Navigate + read params
'use client';
const router = useRouter();
router.push('/about');
// params come from a prop, not router.query
import { useParams } from 'next/navigation';
const { id } = useParams();
Link
import Link from 'next/link';
<Link href="/about">About</Link>
useRouter from next/navigation has no .query — it only has methods like push, replace, back, refresh. Route params/search params need useParams() / useSearchParams() instead, and it only works inside Client Components.

Redirects

Server-side redirects are declared differently in each router.

Pages Router

getServerSideProps redirect
export async function getServerSideProps() {
  const user = null;
  if (!user) {
    return { redirect: { destination: '/login', permanent: false } };
  }
  return { props: {} };
}

App Router

redirect() from next/navigation
import { redirect } from 'next/navigation';
export default async function Dashboard() {
  const user = null;
  if (!user) redirect('/login');
  return <h1>Dashboard</h1>;
}

Metadata & SEO

The Pages Router uses a Head component rendered in JSX. The App Router uses a plain exported metadata object or a generateMetadata() function — no JSX involved.

Pages Router

pages/about.js
import Head from 'next/head';
export default function About() {
  return (
    <>
      <Head>
        <title>About Us</title>
        <meta name="description" content="Learn more." />
      </Head>
      <h1>About</h1>
    </>
  );
}

Metadata is per-page only; nothing is inherited automatically.

App Router — static

app/about/page.js
export const metadata = {
  title: 'About Us',
  description: 'Learn more.'
};
export default function About() {
  return <h1>About</h1>;
}

App Router — dynamic

app/products/[id]/page.js
export async function generateMetadata({ params }) {
  const { id } = await params;
  const product = await getProduct(id);
  return { title: product.title, description: product.description };
}

Metadata declared in layout.js is inherited by every nested page unless overridden.

12

API Endpoints

Backend endpoints live in different places and use a different function signature.

Pages Router — API Routes

pages/api/hello.js
export default function handler(req, res) {
  if (req.method === 'GET') {
    return res.status(200).json({ message: 'Hello' });
  }
  res.status(405).end();
}

One handler function receives (req, res) and branches on req.method.

App Router — Route Handlers

app/api/hello/route.js
export async function GET(request) {
  return Response.json({ message: 'Hello' });
}
export async function POST(request) {
  const body = await request.json();
  return Response.json({ received: body });
}

Each HTTP verb is its own exported function using the Web Request/Response API.

Loading & Error States

The App Router has dedicated file conventions for this; the Pages Router requires manual state management.

Pages Router

Manual loading state
import { useState, useEffect } from 'react';
export default function Products() {
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  useEffect(() => {
    fetch('/api/products')
      .then(r => r.json())
      .then(setData)
      .catch(setError)
      .finally(() => setLoading(false));
  }, []);
  if (loading) return <p>Loading...</p>;
  if (error) return <p>Something went wrong</p>;
}

App Router — file conventions

app/products/loading.js
export default function Loading() {
  return <p>Loading products...</p>;
}
app/products/error.js
'use client';
export default function Error({ error, reset }) {
  return (
    <div>
      <p>Something went wrong</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  );
}

loading.js wraps the segment in a React Suspense boundary automatically; error.js wraps it in an Error Boundary automatically.

Image Optimization

next/image works in both routers with identical props — this is one of the few APIs that did not change.

Pages Router

import Image from 'next/image';
<Image src="/logo.png" width={200} height={100} alt="Logo" />

App Router

import Image from 'next/image';
<Image src="/logo.png" width={200} height={100} alt="Logo" priority />

The priority prop is commonly needed for above-the-fold images used in Server Components (e.g. hero banners) to avoid layout shift.

Caching Behavior

The Pages Router caches per-page based on which data function you export. The App Router caches per fetch call.

Pages Router

  • getStaticProps → cached at build time (SSG)
  • getStaticProps + revalidate → cached, regenerated after N seconds (ISR)
  • getServerSideProps → never cached, runs every request (SSR)

App Router

  • fetch(url) → cached by default (SSG-like, force-cache)
  • fetch(url, { next: { revalidate: 60 } }) → cached, revalidated every 60s (ISR-like)
  • fetch(url, { cache: 'no-store' }) → never cached (SSR-like)
Caching is controlled per fetch call, not per page — different fetches on the same page can use different caching strategies.

Next.js Fundamentals

React (plain)

  • A UI library only — no routing, no data fetching, no bundler built in
  • Create React App (CRA) needs manual setup for routing, SSR, code splitting
  • Everything renders on the client (CSR) by default

Next.js

  • A full React framework: routing, SSR/SSG/ISR, image/font optimization, API routes, and a bundler (Turbopack/Webpack) built in
  • Project created with npx create-next-app@latest
  • Main features: file-based routing, hybrid rendering, built-in CSS support, automatic code splitting, TypeScript support out of the box
Since Next.js 13.4, create-next-app scaffolds the App Router by default; the Pages Router can still be selected/used manually.

Custom Document / Root HTML Shell

Pages Router — _document.js

pages/_document.js
import { Html, Head, Main, NextScript } from 'next/document';
export default function Document() {
  return (
    <Html lang="en">
      <Head />
      <body>
        <Main />
        <NextScript />
      </body>
    </Html>
  );
}

Customizes the base HTML shell (once per app, not per page).

App Router — layout.js replaces it

app/layout.js
export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}

There is no separate _document.js concept — the root layout.js owns the <html>/<body> tags directly.

Dynamic Segment Patterns

Same syntax in both routers

[id] — Single Segment
pages/products/[id].js  →  /products/5
[...slug] — Catch-All (required)
pages/docs/[...slug].js  →  /docs/a/b/c
router.query.slug === ['a','b','c']

Same syntax in both routers

app/products/[id]/page.js
app/products/[id]/page.js  →  /products/5
[[...slug]] — Optional Catch-All
app/docs/[[...slug]]/page.js
matches /docs AND /docs/a/b/c
[...slug] requires at least one segment (no match for the bare route); [[...slug]] (double brackets) also matches the parent route with zero segments. This bracket syntax is identical in Pages and App Router.

App Router-Only Advanced Routing (No Pages Router Equivalent)

These five features do not exist in the Pages Router at all — they're built on the App Router's nested-folder + Server Component model.

Pages Router

❌ Not available. The Pages Router has a flat, single-purpose file-per-route model, so it has no concept of templates, route groups, parallel slots, or intercepting routes.

App Router

template.js — like layout, but re-mounts on every navigation
export default function Template({ children }) {
  return <div>{children}</div>;
}
Route Groups — organize without affecting the URL
app/(marketing)/about/page.js  →  /about
app/(shop)/cart/page.js         →  /cart
Parallel Routes — render independent slots
app/@analytics/page.js
app/@team/page.js
app/layout.js receives both as props
Intercepting Routes — load a route inside the current UI
app/feed/(..)photo/[id]/page.js
// opens /photo/5 as a modal over /feed instead of full navigation

import Link from 'next/link';

forbidden() / unauthorized() (Next.js 15, App Router only)

Pages Router

❌ No built-in equivalent — access control is handled manually, typically via redirect in getServerSideProps or custom middleware.

App Router

unauthorized() — 401, user is not logged in
// app/dashboard/page.tsx
import { unauthorized } from 'next/navigation';
export default async function DashboardPage() {
  const session = await verifySession();
  if (!session) unauthorized();
  return <h1>Dashboard</h1>;
}
forbidden() — 403, logged in but lacks permission
// app/admin/page.tsx
import { forbidden } from 'next/navigation';
export default async function AdminPage() {
  const session = await verifySession();
  if (session.role !== 'admin') forbidden();
  return <h1>Admin</h1>;
}
Matching file conventions (sit next to not-found.js / error.js)
// app/unauthorized.tsx
export default function Unauthorized() {
  return (<div><h1>401</h1><p>Please login to continue.</p></div>);
}
// app/forbidden.tsx
export default function Forbidden() {
  return (<div><h1>403</h1><p>You don't have access.</p></div>);
}

Before Next.js 15 this was done manually — if (!session) return <LoginPage />. Now unauthorized()/forbidden() stop rendering and automatically show unauthorized.tsx/forbidden.tsx, the same way notFound() + not-found.js already worked.

Advanced Caching & Revalidation (App Router)

The Pages Router's only caching control is choosing which data function to export. The App Router has a much larger, granular caching toolkit — none of these APIs exist in the Pages Router.

Pages Router

❌ No fetch-level cache options, no tag-based invalidation, no per-function memoization API. Caching is all-or-nothing per page, controlled only by which of getStaticProps / getServerSideProps you export.

App Router

Extended fetch — force-cache vs no-store
fetch(url, { cache: 'force-cache' }); // cached indefinitely (SSG-like)
fetch(url, { cache: 'no-store' });     // never cached (SSR-like)
fetch(url, { next: { revalidate: 60 } }); // cached, refreshed every 60s
On-demand revalidation via a Route Handler
// app/api/revalidate/route.js
import { revalidatePath, revalidateTag } from 'next/cache';
export async function POST(req) {
  const { path, tag } = await req.json();
  if (path) revalidatePath(path);
  if (tag) revalidateTag(tag);
  return Response.json({ revalidated: true });
}

Called by a webhook from any backend (.NET, Java, a CMS) when content changes, so a non-Next.js system can still invalidate the Next.js cache.

Real architecture: Next.js frontend + separate .NET/Java backend
https://myshop.com        → Next.js app (Server Components, cache, revalidation)
https://api.myshop.com    → .NET / Java backend + database
// app/products/page.tsx — Next.js fetches from the external API and tags the cache
export default async function ProductsPage() {
  const res = await fetch('https://api.myshop.com/products', { next: { tags: ['products'] } });
  const products = await res.json();
  return <div>{products.map(p => <p key={p.id}>{p.name}</p>)}</div>;
}

The product data lives in the .NET/Java database, but the cache belongs to Next.js. When an admin changes a price directly in the external backend, Next.js has no idea — it keeps serving the old cached response until the backend calls the /api/revalidate webhook above with tag: 'products', which is the only way to sync Next.js's cache with a change that happened outside of Next.js.

unstable_cache — cache any async function, not just fetch
import { unstable_cache } from 'next/cache';
const getUser = unstable_cache(
  async (id) => db.user.find(id),
  ['user'],
  { revalidate: 3600, tags: ['user'] }
);
React.cache — per-request memoization (non-fetch)
import { cache } from 'react';
const getUser = cache(async (id) => db.user.find(id));
// called from multiple components in one request → runs once
'use cache' directive (Next.js 15)
async function getPosts() {
  'use cache';
  const res = await fetch('https://api.example.com/posts');
  return res.json();
}
cacheLife / cacheTag helpers
import { unstable_cacheLife as cacheLife, unstable_cacheTag as cacheTag } from 'next/cache';
async function getPosts() {
  'use cache';
  cacheLife('hours');
  cacheTag('posts');
  return fetch('https://api.example.com/posts').then(r => r.json());
}
Request deduplication — automatic
// Same fetch(url) called by 3 different components in one render
// → Next.js sends only ONE network request and shares the result
after() — run code post-response
import { after } from 'next/server';
export default function Page() {
  after(() => logAnalyticsEvent());
  return <div>Page</div>;
}
staleTimes — Router Cache config (next.config.js, 14.2+)
module.exports = {
  experimental: { staleTimes: { dynamic: 30, static: 180 } }
};

  return <button onClick={handleClick}>Add To Cart</button>;
}
Important: router.refresh() does NOT invalidate the data cache — if the fetch is still cached, the refreshed route can still receive the same cached data. Pair it with revalidatePath()/revalidateTag() in the Server Action when the data actually needs to change.

Server Actions (App Router only)

Server Actions have no Pages Router equivalent — mutations there require a separate API route called manually from the client.

Pages Router — the old way

Manual API route + fetch
// pages/api/create-post.js
export default function handler(req, res) {
  if (req.method === 'POST') {
    // save to DB
    res.status(200).json({ ok: true });
  }
}
async function onSubmit(data) {
  await fetch('/api/create-post', { method: 'POST', body: JSON.stringify(data) });
}

App Router — Server Actions

'use server' — mark a function as a Server Action
'use server';
export async function createPost(formData) {
  const title = formData.get('title');
  await db.post.create({ title });
}
Directly wired to a <form>, no API route needed
import { createPost } from './actions';
export default function NewPost() {
  return (
    <form action={createPost}>
      <input name="title" />
      <button type="submit">Create</button>
    </form>
  );
}
useActionState (React 19) — track result/pending state
'use client';
import { useActionState } from 'react';
const [state, formAction] = useActionState(createPost, null);
useFormStatus — pending state inside the form
'use client';
import { useFormStatus } from 'react-dom';
function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving...' : 'Save'}</button>;
}
Validation errors surfaced via useActionState
'use server';
export async function createPost(prevState, formData) {
  if (!formData.get('title')) return { error: 'Title is required' };
  return { success: true };
}
Called from a Client Component
'use client';
import { createPost } from './actions'; // file has 'use server' at top
<button onClick={() => createPost(new FormData())}>Create</button>
Redirect inside a Server Action
'use server';
import { redirect } from 'next/navigation';
export async function createPost(formData) {
  await db.post.create({ /* ... */ });
  redirect('/posts');
}

Became stable inNext.js 14

Performance Optimization (App Router-oriented, some shared)

Shared with Pages Router

next/dynamic — lazy import (both routers)
import dynamic from 'next/dynamic';
const HeavyChart = dynamic(() => import('./HeavyChart'), { ssr: false, loading: () => <p>Loading...</p> });

Available in both routers — the ssr: false option disables server rendering for that component. In the App Router it's used to keep a heavy 'use client' component out of the initial JS bundle.

Prefetching with <Link> — same component, refined internals
Pages Router: prefetches the page's JS + data on viewport visibility.
App Router (since v13): prefetches only the shared/static parts of the route by default; dynamic segments prefetch on hover/tap.

App Router-specific

Granular Suspense boundaries
export default function Page() {
  return (
    <>
      <Header />
      <Suspense fallback={<Skeleton />}>
        <SlowComments />
      </Suspense>
    </>
  );
}

Splits a page into independent streaming chunks so one slow section doesn't block the rest — no equivalent in the Pages Router's all-or-nothing page render.

next/script strategies
import Script from 'next/script';
<Script src="/analytics.js" strategy="afterInteractive" />
// strategies: beforeInteractive | afterInteractive | lazyOnload | worker

Sharing State Between Server & Client (App Router only)

Pages Router

Not a distinct problem — every component is already a Client Component, so React Context and normal state sharing "just work" everywhere.

App Router

Server → Client: pass data as props
// Server Component
export default async function Page() {
  const data = await getData();
  return <ClientChart data={data} />;
}
Why React Context can't be used in a Server Component
Context relies on React's client-side render tree and a Provider
that stays mounted in the browser. Server Components have no
persistent browser instance, so they cannot subscribe to or
provide Context values.
Fix: wrap the Provider itself in a Client Component
'use client';
export function Providers({ children }) {
  return <ThemeContext.Provider value="dark">{children}</ThemeContext.Provider>;
}
Zustand — per-request store pattern
// store must be created INSIDE a Client Component/provider per request
// to avoid leaking state between different users' requests on the server
'use client';
import { createStore } from 'zustand/vanilla';
export const createAppStore = () => createStore((set) => ({ count: 0 }));

App Router-specific (Next.js 15)

Client-Side Data Fetching

Pages Router

import { useEffect, useState } from 'react';
export default function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch('/api/user').then(r => r.json()).then(setUser);
  }, []);

App Router — same pattern, inside a Client Component

'use client';
import { useEffect, useState } from 'react';
export default function Profile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch('/api/user').then(r => r.json()).then(setUser);
  }, []);
  return <div>{user?.name}</div>;
}
SWR (Vercel's data-fetching library) adds caching, revalidation, deduplication, and polling on top of client-side fetch, and is used the same way in both routers: const { data } = useSWR('/api/user', fetcher). Middleware

Pages Router

Middleware runs the same way regardless of router — it's not tied to Pages or App Router internals, since it executes before either one on the Edge, based on a root-level middleware.ts file.

App Router

middleware.ts (project root)
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';
export function middleware(request: NextRequest) {
  const token = request.cookies.get('token');
  if (!token) return NextResponse.redirect(new URL('/login', request.url));
  return NextResponse.next();
}
export const config = { matcher: ['/dashboard/:path*'] };

Runs on the Edge Runtime before a request reaches any route — used for auth checks, redirects, A/B testing, and header rewriting, in either router.

Runtime: Edge vs Node.js

Pages Router

export const config = { runtime: 'edge' }; // in an API route or page

Set per API route/page via an exported config object.

App Router

export const runtime = 'edge'; // or 'nodejs' (default)
export const preferredRegion = 'iad1';

Set via a segment-config export in page.js/layout.js/route.js. Edge Runtime is lighter/faster to cold-start but can't use full Node.js APIs (e.g. some native modules); Node.js runtime supports the full Node API surface.

i18n (Internationalization) Routing

Pages Router — built in

// next.config.js
module.exports = {
  i18n: { locales: ['en', 'fr', 'de'], defaultLocale: 'en' }
};

Next.js automatically generates locale-prefixed routes (/fr/about) and exposes router.locale — fully built in.

App Router — manual, via middleware + folders

app/[lang]/page.js       →  /en, /fr, /de
middleware.ts detects the Accept-Language header and rewrites/redirects to the right [lang] segment

The built-in i18n config key from next.config.js does not apply to the App Router — routing has to be built manually (or with a library like next-intl).
